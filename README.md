# gitops-flux

GitOps configuration for the `25c-shared` dev cluster, managed by [Flux CD](https://fluxcd.io) v2.4.0.

Everything deployed to the cluster is declared in this repository. Flux polls this repo and reconciles the cluster to match `main`. **Do not `kubectl apply` directly** — changes made outside Git will be reverted, and objects not present in Git will be pruned.

- **Git source:** `https://github.com/Ubuntu-25c-market-prep/gitops-flux.git` (branch `main`)
- **Flux version:** 2.4.0
- **Clusters:** 1 (`dev` / `25c-shared`)
- **Components:** sealed-secrets

## Repository layout

```
gitops-flux/
├── clusters/                          # How Flux itself runs (bootstrap layer)
│   ├── base/2.4.0/
│   │   ├── gotk-components.yaml       # Flux CRDs + 6 controllers (generated)
│   │   ├── gotk-sync.yaml             # GitRepository + self-managing Kustomization
│   │   └── kustomization.yaml
│   └── dev/25c-shared/                # Cluster entry point (bootstrap target)
│       ├── kustomization.yaml         # base/2.4.0 + infrastructures.yaml
│       ├── patch.yaml                 # repoints flux-system at this directory
│       └── infrastructures.yaml       # Kustomization -> infrastructures/dev/25c-shared
│
└── infrastructures/                   # What Flux installs (workload layer)
    ├── base/                          # Reusable, environment-neutral definitions
    │   ├── 000-helm-repository/       # Chart sources (HelmRepository objects)
    │   │   ├── sealed-secrets.yaml
    │   │   └── kustomization.yaml     # index of active sources
    │   └── sealed-secrets/
    │       ├── helmrelease.yaml       # chart, version, default values
    │       └── kustomization.yaml
    └── dev/25c-shared/                # This cluster's overrides
        ├── flux-system/               # imports 000-helm-repository
        ├── 000-cluster-wide-resources/
        │   └── namespace/             # Namespace objects
        └── sealed-secrets/
            ├── kustomization.yaml     # inherits base + applies patch
            └── patch.yaml             # dev-only resource limits & labels
```

There is deliberately **no `kustomization.yaml`** at `infrastructures/dev/25c-shared/`. Flux auto-generates one by scanning subdirectories recursively, so a new component directory is picked up without editing an index file.

## Reconciliation flow

```
GitRepository "flux-system"  (polls main every 59m)
   │
   └── Kustomization "flux-system"  →  ./clusters/dev/25c-shared   (every 59m)
         ├── Flux's own controllers          ← Flux keeps itself updated
         └── Kustomization "infrastructure"  →  ./infrastructures/dev/25c-shared   (every 20h)
               ├── flux-system/                → HelmRepository sources
               ├── 000-cluster-wide-resources/ → Namespaces
               └── sealed-secrets/             → HelmRelease
                     └── helm-controller installs the chart into ns `sealed-secrets`
```

## Layer reference

| Path | Purpose |
|---|---|
| `clusters/base/2.4.0/gotk-components.yaml` | Flux install manifest — CRDs and the six controllers. Generated by `flux bootstrap`; never edit by hand. |
| `clusters/base/2.4.0/gotk-sync.yaml` | The bootstrap seed: the `GitRepository` pointing at this repo, and the `Kustomization` that makes Flux manage itself. |
| `clusters/dev/25c-shared/patch.yaml` | Rewrites the `flux-system` Kustomization's `path` to this directory. Without it, Flux would sync only the generic base and never find `infrastructures.yaml`. |
| `clusters/dev/25c-shared/infrastructures.yaml` | Declares the `infrastructure` Kustomization — the bridge from bootstrap layer to workload layer. `prune: true`. |
| `infrastructures/base/000-helm-repository/` | All `HelmRepository` objects — *where charts come from*. Numeric prefix ensures sources reconcile before the releases consuming them. |
| `infrastructures/base/<component>/` | The `HelmRelease` — chart name, pinned version, environment-neutral values. |
| `infrastructures/dev/25c-shared/flux-system/` | Imports `base/000-helm-repository` into the reconciliation path. Sources exist in base but are not applied until an overlay opts in. |
| `infrastructures/dev/25c-shared/000-cluster-wide-resources/` | Namespaces and other cluster-scoped objects. |
| `infrastructures/dev/25c-shared/<component>/` | The overlay: inherits base, patches in environment-specific values. |

## Adding a new component

Three steps. Step 1 is in a different directory from the rest and is the one most often forgotten.

**1. Add the chart source** — only if that vendor's repo isn't already present.

`infrastructures/base/000-helm-repository/<vendor>.yaml`
```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: HelmRepository
metadata:
  name: <vendor>
  namespace: flux-system
spec:
  interval: 24h
  url: https://example.github.io/charts
```

Then register it in `infrastructures/base/000-helm-repository/kustomization.yaml` under `resources:`.

One `HelmRepository` can serve several charts — reuse an existing entry rather than duplicating a URL.

**2. Define the component in base**

`infrastructures/base/<component>/helmrelease.yaml`
```yaml
apiVersion: helm.toolkit.fluxcd.io/v2
kind: HelmRelease
metadata:
  name: <component>
  namespace: flux-system
spec:
  chart:
    spec:
      chart: <chart-name>
      version: "1.2.3"           # always pin
      sourceRef:
        kind: HelmRepository
        name: <vendor>           # must match step 1
        namespace: flux-system
  interval: 20h0m0s
  install:
    createNamespace: true
  targetNamespace: <component>
  values:
    # environment-NEUTRAL defaults only
```

Plus a `kustomization.yaml` listing `helmrelease.yaml`.

**3. Create the overlay**

`infrastructures/dev/25c-shared/<component>/kustomization.yaml`
```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: <component>
resources:
  - ../../../base/<component>
patches:
  - path: patch.yaml
    target:
      kind: HelmRelease
labels:
  - pairs:
      kustomize.toolkit.fluxcd.io/prune: enabled
```

`patch.yaml` carries the dev-specific bits — resource requests/limits, replica counts, hostnames, labels.

If the component needs a namespace declared explicitly, add it under `000-cluster-wide-resources/namespace/`.

**Verify before committing:**
```bash
kustomize build infrastructures/dev/25c-shared/<component>
kustomize build infrastructures/dev/25c-shared      # whole overlay
```

## Conventions

| Convention | Reason |
|---|---|
| `000-` directory prefix | Reconcile order — sources and namespaces before their consumers |
| `base/` holds no environment values | Keeps base reusable when a `prod/` overlay is added |
| Flux version as a directory (`2.4.0`) | Side-by-side upgrades; rollback is a one-line path change |
| First line of each kustomization is its own path, as a comment | A file opened alone is still locatable |
| Chart versions always pinned | No surprise upgrades on reconcile |
| `kustomize.toolkit.fluxcd.io/prune: enabled` label | Marks objects Flux may garbage-collect |

## Common operations

```bash
# Overall health
flux get all -A

# Force an immediate sync (default intervals are long — see Notes)
flux reconcile source git flux-system
flux reconcile kustomization infrastructure --with-source

# Inspect a component

# Why is something not applying?
flux logs --level=error --all-namespaces
```

## Working with sealed-secrets

Plain `Secret` objects must never be committed. Encrypt them first — a `SealedSecret` is safe in Git because only the controller in this cluster can decrypt it.

```bash
# Encrypt
kubectl create secret generic my-secret \
  --from-literal=password=... --dry-run=client -o yaml \
  | kubeseal --controller-namespace sealed-secrets --format yaml \
  > my-sealedsecret.yaml

# Commit my-sealedsecret.yaml; the controller creates the real Secret in-cluster.
```

The controller's private key lives in the `sealed-secrets-key` secret in the `sealed-secrets` namespace. **Back it up** — losing it means every committed `SealedSecret` becomes undecryptable and must be regenerated.

## Working with Istio

`istiod` is installed **revisioned** (`revision: 1-30-3`), not with the default/unrevisioned tag. That makes injection opt-in by construction — no namespace gets a sidecar unless it explicitly asks for this revision.

To enroll a namespace:

```bash
kubectl label namespace app-storefront istio.io/rev=1-30-3
```

Pods created *after* the label is applied get a sidecar. Existing pods in a newly-labeled namespace do not — restart them (`kubectl rollout restart deployment/...`) to pick it up.

`revisionTags: [default]` tags `1-30-3` as the default revision — not to make the older `istio-injection=enabled` label the recommended path, but because `istiod`'s chart always creates `istiod-default-validator`, a `ValidatingWebhookConfiguration` for `Gateway`/`VirtualService`/etc admission that expects a plain `istiod` Service to exist. With no revision tagged `default`, that Service never gets created and **every** such object fails admission outright (`failurePolicy: Fail`): `service "istiod" not found`. This is standard practice for a single-revision install, not a workaround.

Side effect: `istio-injection=enabled` now works too, resolving to whichever revision is tagged `default`. Prefer `istio.io/rev=1-30-3` anyway — it's explicit about which revision a namespace is pinned to, which matters once `gitops-flux#29`'s second revision exists and `istio-injection=enabled` could silently follow the tag to either one.

```bash
# Verify: after restarting workloads, every pod should show 2/2 (app + istio-proxy)
kubectl -n app-storefront get pods
```

When a second revision exists (`gitops-flux#29`, the upgrade rehearsal), moving a namespace between revisions is the same command with the new revision's label value — Istio does not support two `istio.io/rev` labels on one namespace at once.

## Notes

- **Sync latency.** The `infrastructure` Kustomization runs on a 20h interval, so a commit may take up to 20 hours to land on its own. Use `flux reconcile` when you need it now, or lower the interval in `clusters/dev/25c-shared/infrastructures.yaml`.
- **Pruning is on.** Deleting a file from Git deletes the object from the cluster. Intended behavior, but be deliberate with `git rm`.
- **Multi-environment ready.** A second cluster means a new `clusters/<env>/<name>/` and `infrastructures/<env>/<name>/`, reusing `base/` unchanged. Do not edit `base/` to solve a single-cluster problem.
- **Chart repo URL.** sealed-secrets moved from the `bitnami-labs` GitHub org to `bitnami`; `https://bitnami.github.io/sealed-secrets` is current. Older examples referencing `bitnami-labs.github.io` now 404.
